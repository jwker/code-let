# 产品 agent 的原型预览继续用原生视图，不改成 iframe

产品 agent 的区域 6 保持现有的 `WebContentsView`，标注靠 preload 往页面里注入脚本、事件经 IPC 回主进程。
不照搬隔壁 `FileViewer` 的沙箱 iframe：那个方案里原型必须是单文件自包含 HTML（`srcDoc` 的文档地址是
`about:srcdoc`，相对路径加载不了），并且会丢掉 `browser_screenshot` / `browser_click` 这些已经能用的能力。

## Considered Options

- **iframe + `srcDoc`**：交互全部落在 DOM 里，Playwright 的 `frameLocator` 能直接断言，通道只是
  `postMessage`。代价是原型里的图片、字体、样式表全都加载不了，等于要求 agent 写自包含单文件。
- **iframe + 自定义协议**（`codelet-prototype://`）：保留真实文档地址和相对路径。代价是要在 `app.ready`
  之前做协议特权注册（未实测），并且产品 agent 的区域 6 要从 `BrowserPane` 拆成新组件。
- **原生视图**（采用）：改动只有一个 preload 和一对 IPC 事件，区域 6 的形态、地址栏、agent 的截图能力
  全部原样保留。

## Consequences

- 高亮和角标只能注入到页面里画，React 画不到原生视图上面。注入的脚本要写成**跟传输无关**的：它只负责
  「发现了点击 → 调用一个 `post(message)`」，`post` 是 `ipcRenderer.send` 还是 `window.parent.postMessage`
  由外壳决定。以后真要迁到 iframe，搬的是外壳。
- e2e 不能靠截图比对。测法是 Playwright 用 `app.evaluate()` 进主进程，主进程在页面里执行脚本拿矩形、
  用 `webContents.sendInputEvent()` 派发合成的 hover 和点击、再读回 DOM 状态断言——形状照 `e2e/browser.spec.ts`
  里调 `__codeletBrowser` 的写法。
- 真正测不到的只剩像素外观（描边粗细、配色、角标位置）。这部分归设计稿，不写断言。
