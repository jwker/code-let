# 基础 agent 的定义是数据，内置三个写死在代码里

用户新增的基础 agent（名字、说明、颜色、提示词）存在 `<userData>/agentTypes.json`；
基础、开发、产品这三个内置的定义是 `contract/` 里的常量、**不落盘**。一个类型能做什么
（预览、自动归档、区域 5/6 的布局）不放进数据里，而是由一个按内置 id 判定的能力函数给出，
用户不能配置。`AgentRecord.type` 存字符串；类型找不到定义时记录**保留**，界面按
「未知 agent」只读显示。

## Considered Options

- **全部类型都落盘、都可编辑**：数据形状统一，但能力字段必须跟着代码版本迁移——
  用户能造出「预览开关开着、功能却不存在」的类型，且每加一个内置能力都要写迁移。
- **`AgentType` 继续是闭合联合，新增类型要发版**：类型安全最好，但用户不能自己新增，
  与需求相反。
- **采用：内置常量 + 用户数据 + 能力函数**：名字、颜色、提示词是纯展示与文本，
  放进数据没有风险；能力和代码强绑定，留在代码里。

## Consequences

- 判断「要不要开预览」这类问题不能比较类型字符串，只能问能力函数。界面里出现
  `type === 'product'` 就是要改的地方。
- `PANE_LAYOUT` 原来是 `Record<AgentType, PaneLayout>`，改成按能力取值之后，
  `tests/agents.test.ts` 里断言「恰好七个键」的那条要改。
- 「通用」改名「基础」，代码 id 保持 `general` 不变，所以磁盘上的旧记录不用迁移、
  旧默认名（「通用 1」）照旧显示。
- 记录不能因为类型不认识就丢弃：`readRecord` 原来会整条丢掉，那等于「删一个类型 =
  删掉所有用它的 agent」。
