# 从图片里读设计

这份文档讲的是：手上只有一张界面截图（参考图、竞品截图、设计稿渲染图），
怎么把它变成能实现的具体数值。

写它的原因很直接：**没量就画，会整段返工。** 一次外壳改版的设计稿，
凭眼睛判断了三个结论（面板紧贴、只有一个圆角、标签填满高度），全部是错的，
量过像素之后才发现真实结构完全不同。

---

## 一、三种提取手段，可靠度差很多

### 1. 像素级测量

把图片读成位图，逐像素取颜色。在 Electron 里：

```js
const img = nativeImage.createFromPath('shot.png')
const b = img.toBitmap()
const hex = (x, y) => {
  const i = (y * width + x) * 4
  return '#' + [b[i], b[i + 1], b[i + 2]].map((v) => v.toString(16).padStart(2, '0')).join('')
}
```

**不要取单点。** 单个采样点很容易落在文字笔画、图标线条或抗锯齿的边缘上，
拿到的色值没有意义。第一次采样得到一堆 `#787878`、`#8a8a8a`，全是文字的颜色。

**用扫描线。** 沿一行（或一列）走一遍，记录每次颜色变化的位置：

```js
let prev = null
for (let x = 0; x < width; x++) {
  const c = hex(x, y)
  if (c !== prev) {
    segments.push({ x, color: c })
    prev = c
  }
}
```

一条扫描线同时给出四样东西：

- 元素的左右（或上下）边界
- 元素之间的缝隙宽度
- 边框的位置和粗细
- 边框自己的颜色

扫描多条线就能还原整个区块的盒模型。判断「卡片之间是不是有缝、缝多宽」，
横扫一张卡片中间那一行，看有没有一段背景色的窄条就够了。

### 2. 几何测量

对**自己渲染出来的页面**（设计稿 HTML、真实应用窗口），用
`element.getBoundingClientRect()` 量：

```js
const a = document.querySelector('.card-a').getBoundingClientRect()
const b = document.querySelector('.card-b').getBoundingClientRect()
// 两个元素之间的实际间距
const gap = b.top - a.bottom
// 是否顶部对齐
const aligned = Math.abs(a.top - b.top) < 1
```

这比像素测量更准，因为不涉及抗锯齿、色彩空间、图片压缩。局限是只能量自己画的
东西 —— 参考图没有 DOM。

两者的分工：**参考图用像素测量，自己的稿子和真实界面用几何测量。**

### 3. 目测

有些东西量不出来，只能看：

- 图标是线性描边还是实心填充
- 圆角是「轻微」还是「明显」
- 阴影几乎没有，还是有明显存在感
- 整体密度偏疏还是偏密
- 视觉重心在哪

这一类的判断最容易出错，因为它们没有客观数值可依。**遇到目测结论和实测数字
冲突时，信数字。**

## 二、提取哪些元素

按四类分。

### 1. 颜色

| 类别 | 怎么得到 | 注意 |
|---|---|---|
| 层级底色 | 扫描线里面积最大的那一段 | 要记的是**相邻两层的差值**，不是绝对值 |
| 边框色 | 扫描线里那条 1px 的段 | 常比背景深一档 |
| 组件填充 | 组件内部的色值 | 药丸、按钮、输入框 |
| 文字色阶 | 文字笔画中心的色值 | 有抗锯齿，取最深的那个点 |

**关键在差值，不在绝对值。** 一个浅色画布 `#FAFAFA` 上放白色卡片 `#FFFFFF`，
两者只差 4–5/255 —— 正是这个微小的差让卡片「浮」得起来。差到 20 就显脏，
差到 2 以下就浮不起来。

同一张图里通常有 4–6 个层级：最底（画布）、面板、卡片、浮层（菜单/弹窗）、
凹陷（输入框/代码块）。每一层都比上一层亮一点（暗色主题反过来）。

### 2. 尺寸

都是 CSS px。**先确认图片的缩放倍数** —— Retina 截图是 2x，
3024×1778 的图对应 1512×889 的窗口。不换算会得出「标题栏 88px」这种数字。

| 项 | 怎么量 |
|---|---|
| 区域高度 | 竖扫，找底色变化的位置 |
| 栏宽 | 横扫 |
| 元素间距 | 横扫，找中间那段背景色 |
| 边框粗细 | 扫描线里单像素的段 |
| 圆角半径 | 沿对角线扫，找弧线终点；或者目测后反向量验证 |
| 组件高度 | 竖扫组件的上下边界 |

### 3. 层级关系（Z 轴）

这是最容易被忽略、但决定性的部分。要回答四个问题：

1. **谁是底，谁是浮在上面的？**
2. **靠什么浮起来？** 边框？圆角？四周留缝？阴影？`
3. **区块之间靠什么分界？** 色阶差 / 1px 竖线 / 背景色缝隙 / 圆角断点
4. **底槽和面板是不是同一层？** 标题栏、侧边轨这类「背景」和卡片这类「面板」，
   通常是不同的层

一道判断题：**如果两个区块之间是「缝隙」而不是「线」，它们就是两块独立的板；
如果是「线」，它们是同一块板上的分区。** 这两种读法在视觉上差别很大。

### 4. 形态语言

- **组件形状**：药丸（浮在背景上的圆角小块）还是填满容器（贴边、占满高度）
- **图标风格**：线性描边还是实心填充，线宽多少
- **字号阶梯**：相邻两档差多少（常见是 1px，比如 9.5 / 10.5 / 11.5 / 12.5）
- **密度**：一行能放几个同类元素、留白占多大比例

形态语言决定了「同一套布局看起来像哪个产品」。布局可以一样，
药丸和贴边标签会让界面读起来完全不同。

## 三、工作顺序

1. **先量，后看。** 拿到图先扫几条线，把颜色和边界拿到手，再退后看整体。
   反过来（先看整体形成印象，再去验证）容易把印象当结论。

2. **找可量的锚点。** 不要「大概 44px」，要「竖扫发现 y=87 处颜色变了，87 ÷ 2 ≈ 44」。

3. **画出来反向量自己。** 稿子渲染后，用几何测量量一遍，跟参考图的数字对。

4. **多状态各画一遍。** 一张图只呈现一个状态。关键组件的每个状态
   （展开 / 收起 / hover / 空 / 加载）都要单独画，很多设计问题只在某个状态暴露。
   曾经有一版稿子所有方案都只画了展开态，收起后的入口去哪完全没交代。

## 四、一次失误的复盘

外壳改版的第一版设计稿，凭眼睛得出三个结论：

| 判断 | 实际 |
|---|---|
| 面板紧贴轨和标题栏 | 四周留 7px 缝 |
| 只有一个左上角圆角 | 每张卡四个角都圆 |
| 标签填满标题栏高度 | 药丸浮在背景上，高 22px |

三条全错，整个 Z 层级理解反了。量过之后得到的数字：缝隙 7px、边框 1px、
药丸高 22px、边框色比背景深一档。

**根因不是眼力差，是没量。** 这些数字看图看不出来，但扫一遍就知道。
后来第二版改了做法 —— 先扫描线，再画 —— 一次就对了。

## 五、方法的边界

**能量准的**：颜色、尺寸、边界、间距、层级关系、对齐。

**量不准的**：

- **动效**：过渡时长、缓动曲线、滚动的惯性 —— 静态图里没有
- **交互态**：hover / focus / active / disabled 的样式
- **视觉重心**：留白看起来「很舒服」，可能只是因为图里内容少
- **真实密度**：参考图可能是 1440 宽的窗口配一份短文档；真机上内容一多，
  观感完全不同

**一张图的局限**：它只呈现一个状态、一个视口尺寸、一种内容量。
超出这三样的一切，都是推断，不是事实。做设计判断时要把这句话记住。

**遇到冲突时**：实测数字优先于目测印象，真实渲染优先于参考图推断。
