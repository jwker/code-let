AI 回复元信息行 · 局部方案稿

回复下方的三个数据：复制 · token · 用时

这份稿只画 AI 回复正文下方那一小块 —— 正文、工具轨迹、输入框都不在范围内。 四个方案共用同一条回复作为上下文，方便横向比较；每个方案后面标注它适合什么场景、以及要落地时缺什么数据。

口径约定：token 分「输出」与「缓存命中」两栏，缓存单独标，不并进消耗； 用时从请求发出算到该条回复结束，流式过程中实时递增。

方案 A · 尾注式

最轻的一版。元信息常驻在正文末尾，复制按钮默认不显示，鼠标悬停整条回复时淡入。正文多的时候几乎不占视觉重量。

方案 B · 工具条

三件事收进一个胶囊里，左边复制、右边数字。边界清晰，一眼能看出「这一条回复的操作区在哪」，点复制有明确落点。

方案 C · 胶囊分组 + 展开明细

三件事各占一个 chip，token 与耗时可以点开看明细（输入/输出/缓存分别多少、耗时拆成首字与生成）。适合把统计当正经信息读的人。

方案 D · 一行汇总 + 抽屉明细

默认只有一行汇总（总 token · 用时），点它展开一整块明细，把复制、token 构成、耗时构成都放进去。页面最安静，需要时才看细节。

这一轮不做

项为什么
成本（金额）显示各家模型计价不同，同一条回复算出来的钱对不上用户预期；先只给 token。
多条回复对比视图那是另一个页面（会话统计），不是回复下方的局部。
复制工具输出复制只针对这条 AI 回复的正文，工具输出单独有各自的操作。
逐 token 明细要拿到每步的 token 分布得改协议，收益低。
